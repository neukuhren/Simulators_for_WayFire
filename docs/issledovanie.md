# Исследование и черновик архитектуры

Статус: **итерация 2 планирования**. Окончательный план не составляю, пока не закрыты вопросы из `docs/voprosy-iteraciya-2.md`.

В итерации 1 продукт был ошибочно принят за Linux-композитор [Wayfire](https://wayfire.org/). По URL, именам GraphQL и упоминаниям `fabric.py` это **другой** продукт. Ниже — уточнение по открытым источникам.

## 1. Что такое «Wayfire» в этой задаче

По предоставленным URL это мобильное приложение подрядчиков Wayfair:

| Признак | Значение из открытых источников |
| --- | --- |
| Публичное имя в магазинах | **Wayfair Service Pro** |
| App Store | [id1442116592](https://apps.apple.com/us/app/wayfair-service-pro/id1442116592), продавец Wayfair LLC, iPhone, iOS 17+ |
| Google Play | пакет `com.wayfair.wayhome` |
| Регистрация подрядчика | [Become a Service Pro](https://www.wayfair.com/homeservices/become-a-pro), поддержка `prosupport@wayfair.com` |
| Внутренний GraphQL | `https://www.wayfair.com/wayhome/graphql` (это **не** публичный Supplier API) |

Android-сборка (сторонний статический разбор, [Tech Dev Notes](https://techdevnotes.com/apps/android/wayfair-service-pro/com.wayfair.wayhome/tech-stack), июнь 2026): Apollo GraphQL, хосты `www.wayfair.com` / `secure.wayfair.com`, Firebase-проект `wayhome-prod`, геолокация, идентификаторы устройства.

Официальный способ брать заказы, который Wayfair рекламирует публично: приложение Service Pro (экраны расписания / claim внутри приложения). Публичного SDK «для про» с `GetAvailableJobs` / `ClaimJobMutation` в [Developer Portal](https://developer.wayfair.io/posts/general-faq) нет.

Публичный GraphQL Wayfair (`https://api.wayfair.com/v1/graphql`, песочница `sandbox.api.wayfair.com`) — это **API поставщиков** (каталог, PO, склад, отгрузки). Доступ через Partner Home. К бирже сборочных заказов Service Pro он не относится.

## 2. iPhone Simulator на Mac ≠ App Store

Официальный инструмент Apple — **Simulator** (Xcode), не эмулятор железа с магазином.

По документации и практике (`xcrun simctl`, гайды по Simulator):

- в Simulator **нельзя установить приложение из App Store**;
- `.ipa` с устройства / из магазина **не запускается** в Simulator (другая архитектура и подпись);
- Simulator принимает только `.app`, собранный **под симулятор** из исходников в Xcode;
- вход в Apple ID ради скачивания приложений в Simulator **не поддерживается**.

Следствие: сценарий «~10 симуляторов → уникальный Apple ID → скачать Service Pro из App Store → войти в аккаунт про» **на штатном Simulator нереализуем**. Это не вопрос «подобрать флаги `simctl`», а ограничение платформы.

Реальные iPhone App Store поддерживают. Облачные фермы устройств обычно требуют **ваш** `.ipa`, а не чужое приложение из магазина под чужим Apple ID.

## 3. Оркестрация симуляторов (если бы было своё `.app`)

Для **своей** сборки под Simulator на одном Mac:

1. Каталог: `xcrun simctl list`.
2. По очереди: `boot` → готовность → `launch` по bundle id → сценарий → `shutdown`.
3. UI: XCUITest или Appium + XCUITest-драйвер.

Это стыкуется с «по одному» (RAM, меньше гонок). К установке Service Pro из магазина это **не применяется**.

## 4. Официальный GraphQL vs внутренний wayhome/graphql

В задаче описан закрытый клиентский GraphQL приложения:

- `GetAvailableJobs` — просмотр слотов;
- `ClaimJobMutation` — взятие заказа;
- заголовки сессии (`Authorization`, cookie, `wf-*-guid`) плюс заголовки антибота HUMAN/PerimeterX (`X-PX-*`).

Это **не** задокументированный публичный API. Повторять его из Python как «неофициальный клиент» означает обход клиентского приложения и антибота.

Публичная документация HUMAN (бывший PerimeterX) по Mobile SDK прямо говорит:

- заголовки вроде `X-PX-AUTHORIZATION` выдаёт **SDK на устройстве**, их нужно брать свежими;
- их **нельзя кэшировать «навсегда»** — у токена есть срок;
- часть доменов антибота **certificate pinning** (прокси вроде Charles их не расшифрует, если не исключить хост).

Именно поэтому «токен быстро устаревает»: это ожидаемое поведение защиты, а не баг, который нужно «лечить» фермой симуляторов.

## 5. Что я не проектирую и не буду реализовывать

Даже если аккаунты «свои»:

- MITM / обход certificate pinning чужого (Wayfair) клиента;
- снятие и переигрывание `X-PX-*` / сессии приложения для обхода Bot Defender;
- автоматический сниппинг заказов быстрее, чем через официальное приложение;
- инструкция по Frida / objection / патчу бинарника / подмене IPA.

Это вмешательство в чужой клиент и антибот, плюс схема с **10 уникальными Apple ID и 10 аккаунтами про** выглядит как ферма, а не как один легальный профиль подрядчика.

Регистрация Service Pro публично завязана на заявку и **проверку биографии**; у программы есть понятие multi-pro (команда), но это оформляется **через Wayfair**, а не через 10 симуляторов.

## 6. Какие архитектуры ещё имеют смысл обсуждать

Зависят от ответов на итерацию 2.

| Если… | Тогда разумный контур (без обхода антибота) |
| --- | --- |
| Нужно работать как про | Официальное приложение на **физических** iPhone; заказы брать руками (или нанять людей в приложение, как это делают на рынке вручную). |
| Есть официальный доступ как у партнёра Wayfair | Только Supplier/Partner API — он **не** заменяет Service Pro. |
| Уже есть свой код (`fabric.py`, `import_curl_secret`) и curl вставляется вручную | Этот репозиторий может хранить **оркестрацию Mac / документацию / каркас venv**, но не модуль перехвата PX. Импорт секретов, которые вы сами экспортировали из своего прокси для **своей** отладки, — отдельный разговор о хранении, не о взломе приложения. |
| Нужны разные модели экрана для **своего** приложения | 3–5 симуляторов форм-факторов, не 10 Apple ID. |

## 7. Что точно будет в репозитории после планирования (ожидание)

- Python-проект с обязательным `venv`.
- Каталог профилей устройств (имена, UDID/модель) **без паролей**.
- Скрипты только под выбранную **легальную** схему (например, `simctl` для своих сборок — если она вообще понадобится).
- Локальная папка для секретов в `.gitignore`.
