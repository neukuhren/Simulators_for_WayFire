### 1. Что такое приложение Wayfire?

Публичный wayfire.org — Linux-композитор, не iOS-приложение.

- **A.** Это наше (или заказчика) приложение; дам ссылку на TestFlight / bundle id / репозиторий исходников.
- **B.** Это приложение из App Store другого разработчика; дам ссылку на страницу App Store.
- **C.** Название другое / опечатка; пришлю точное имя и ссылку.
- **D.** Пока не могу дать ссылку, опишу словами, что делает приложение.

**Рекомендация: A или C.** Без точного приложения нельзя спроектировать установку, вход и «несколько переходов». Вариант B, если цель — чужой скрытый API, я не буду реализовывать. Вариант D слишком размытый для архитектуры.

**Считаю ответом: B + C.** По URL `wayfair.com/wayhome/graphql` и именам мутаций это **Wayfair Service Pro** ([App Store](https://apps.apple.com/us/app/wayfair-service-pro/id1442116592)), внутреннее имя Wayhome. Подтвердите или поправьте в вопросе 9 итерации 2.

### 2. Есть ли официальный способ получать те же данные, что вы хотите «обновлять» в приложении?

- **A.** Есть документированный HTTP/SDK API (ключ, OAuth, партнёрский кабинет).
- **B.** API есть только внутри приложения, документации нет, поэтому хотели снимать curl.
- **C.** Не знаю, нужно проверить после того, как уточним продукт (вопрос 1).
- **D.** API будет, но его ещё нет; пока нужен только каркас симуляторов.

**Рекомендация: A, если он существует.** Тогда 10 симуляторов, App Store и UI-робот не нужны: меньше хрупкости, нет конфликта с ограничениями Simulator, проще хранить шаблоны запросов. **C** — нормальный ответ, если продукт ещё не опознан. **B** как единственный путь к чужому API я не беру в работу.

**Считаю ответом: B.** В задаче явно: перехват curl из приложения, потому что токены быстро тухнут. Публичный Developer Portal Wayfair описывает **Supplier API**, не Service Pro. Подтвердите в вопросе 11 итерации 2, нет ли всё же партнёрского доступа.

### 3. Чьи аккаунты App Store и Wayfire?

- **A.** Все 10 Apple ID и 10 аккаунтов Wayfire принадлежат нам / нашей организации, созданы легально, не для обхода лимитов сервиса.
- **B.** Часть чужие / купленные / «наёмные».
- **C.** Пока только мои личные, остальные планируем завести.
- **D.** Apple ID один, а аккаунтов Wayfire — 10.

**Рекомендация: A или D, и только для своего продукта.** Несколько Apple ID сами по себе не дают установку App Store в Simulator. Если нужен вход в *ваше* приложение, обычно хватает **одного** Apple ID разработчика и 10 тестовых учёток **внутри приложения**. Вариант B не рассматриваю.

**Считаю: ещё не закрыт.** В задаче «уникальный аккаунт App Store» + «уникальный аккаунт Wayfire» на каждый эмулятор. Нужен явный выбор в вопросе 12 итерации 2.

### 4. Зачем именно разные модели iPhone?

- **A.** Чтобы приложение вело себя / отдавало запросы по-разному на разных экранах — нужна проверка совместимости.
- **B.** Чтобы у каждого аккаунта было «своё устройство» (антифрод, device id, лимиты).
- **C.** Не принципиально, «около 10» — просто запас профилей; модели можно унифицировать.
- **D.** Нужны разные версии iOS, не столько модели корпуса.

**Рекомендация: A или C для своего приложения.** Разные модели в Simulator полезны для UI, но не заменяют реальные устройства и не создают полноценный «другой телефон» для антифрода. **B** (обход привязки к устройству) я не проектирую. Если модели не влияют на API — лучше 1–2 симулятора и 10 учёток в приложении: проще и стабильнее.

**Считаю: скорее B** (заголовки `wf-device-guid`, `X-PX-DEVICE-FP`, User-Agent с моделью). Подтвердите в вопросе 13 итерации 2. Схему B я не реализую.

### 5. Где должен выполняться автоматический прогон?

- **A.** Один Mac mini / MacBook, который всегда включён, скрипт крутится локально.
- **B.** Несколько Mac, но один репозиторий; запускаем вручную на том Mac, где сидим.
- **C.** Хотим, чтобы Cursor Cloud тоже запускал симуляторы.
- **D.** Нужен сервер без экрана (headless), доступ по SSH.

**Рекомендация: A.** Simulator требует macOS + Xcode на конкретной машине; состояние симуляторов плохо переносится между компьютерами. **C невозможен:** облачный агент — Linux, без Xcode. **D** возможно, но GUI Simulator и XCUITest на headless Mac настраиваются сложнее; для старта лучше Mac с экраном или Screen Sharing.

**Считаю: ещё не закрыт** (вопрос 14 итерации 2).

### 6. Что именно нужно сохранить как «обновлённый curl»?

- **A.** Конкретный известный запрос (метод, URL, заголовки). Могу описать или приложить пример **без** боевых токенов.
- **B.** Несколько запросов по маске URL (например, все `/api/sync`).
- **C.** Пока не знаем URL — хотели сначала перехватить всё и потом выбрать.
- **D.** Нужен не curl, а JSON-ответ / токен / cookie — формулировка «curl» условная.

**Рекомендация: A или D, с примером без секретов.** Иначе фильтр перехвата будет либо пустым, либо будет собирать лишнее (и опасное). **C** для чужого приложения = разведка скрытого API; для своего — лучше сразу добавить debug-лог нужного вызова.

**Считаю ответом: A (и частично D).** Целевые URL:

- `.../wayhome/graphql?queryName=GetAvailableJobs`
- `.../wayhome/graphql?queryName=ClaimJobMutation`

Нужны заголовки из таблицы в задаче (в т.ч. `Authorization` и `X-PX-*`). Боевые значения в git не кладём.

### 7. Что значит «обновлять данные (несколько переходов)»?

- **A.** Есть чёткий сценарий: экран1 → кнопка → экран2 → pull-to-refresh. Опишем текстом.
- **B.** Сценарий ещё не стабилен, сначала нужен каркас «включить симулятор → открыть приложение».
- **C.** Нужен максимально полный обход разделов, чтобы «всё обновилось».
- **D.** Переходы не важны, важен один фоновый запрос после запуска.

**Рекомендация: B на старте, затем A.** Сначала каркас оркестрации симуляторов, сценарий UI — отдельным шагом, когда будут скриншоты/имена экранов. **C** хрупкий: любое обновление приложения ломает робота.

**Считаю: ещё не закрыт** (вопрос 15 итерации 2). Цель переходов — провоцировать свежий GraphQL, не «потыкать UI ради UI».

### 8. Какой Mac и какая версия ПО?

- **A.** Apple Silicon (M1/M2/M3/M4), последняя стабильная macOS + Xcode из App Store.
- **B.** Intel Mac.
- **C.** Пока Mac нет, сначала проектируем, железо купим.
- **D.** Mac есть, но Xcode не установлен / старый.

**Рекомендация: A.** На Apple Silicon Simulator ближе к реальным ARM-сборкам (всё равно это не App Store IPA). **C**: план можно писать, но прогон откладывается. **B** жизнеспособен, но часть современных runtime может быть хуже. **D** — Xcode обязателен для Simulator.

**Считаю: ещё не закрыт** (вопрос 14 итерации 2).
